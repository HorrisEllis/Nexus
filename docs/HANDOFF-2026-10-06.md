## AR1: the ladder learns (James: "like needs to learn from this: routing and adapting")
Before this, a phase build's escalation ladder was the same fixed order every time: Ollama smallest first, then the agents. It learned nothing. Only chunk routing (`plan()`, from the economy ledger) learned.

- **`lib/agent-record.js`** is a projection over `idearium_phase_runs` plus the reverted and rejected injects. It stores nothing. For each agent it records:
  - **landed:** the agent's files came back;
  - **proven:** the phase's proof run passed, weighted ×2;
  - **undone:** the person reverted or rejected a file it wrote, weighted ×2 bad;
  - **failed:** with the cause (`classify`);
  - **size bucket:** small under 4k, medium under 12k, large;
  - **limit:** at least 2 size-shaped failures at or above a size, and never landed there.
- **`orderLadder`** orders the rungs as follows:
  - an agent past its size limit goes last;
  - otherwise the higher Beta-posterior score goes first, per size bucket where there is enough data;
  - an agent with fewer than `minRecords` attempts sits at 0.5;
  - ties keep the configured order.

  With nothing learned, the ladder is exactly as configured. `routing.ladder_learn: false` turns learning off.
- **`_phaseBuild`** puts the route on the building row: the order and the reason for each agent. Every attempt row now carries `promptChars`.
- **New route:** `GET /api/routing/agents`.
- **Plan panel:**
  - each run shows its route (`_ppRoute`);
  - a new section, "agents · what Nexus has learned", shows a table of landed, proven, undone, failed, limit and score.
- **Tests:**
  - new: `test-agent-record`, 16/16, which replays BL15;
  - still passing: pipeline-routing, escalation-ladder, phase-actually-builds, prove-loop, build-surface, work-surface and the other routing suites.

**Not yet:**

## AR2: faults are first-class data (James: "Failure modes and faults are still first class data.")
AR1 had turned failures into counts and a score. Now each failure is its own `fault_log` record, written through `lib/fault-log.js` `logFault`. That is the existing single writer, and it raises fault-taxonomy friction for known classes such as timeout.

- **`lib/phase-faults.js`.** `modeOf` maps a phase-run row to a failure mode:
  - no-snapshot
  - one of the `classify` causes: timeout, empty, provider-down, …
  - wrote-nothing
  - missed-files
  - blocked
  - tool-errors
  - unproven
  - no-proof
  - ladder-exhausted (logged with no agent)

  Each record carries the agent, the phase, the map, the rung, `promptChars`, the error and `causedBy` (the run row).
- **Hook.** In `idearium/api/index.js`, `appendRow` wraps the db writer. Every `idearium_phase_runs` row that is a fault is also logged, so no failure path can skip it.
- **`lib/repo-inject.js`.** Two more failure modes are logged here: `reply-collapse` (the refused bare-path or sliver block) and `undone` (an agent's change reverted or rejected by the person; the person's own proposals are not logged).
- **Before acting.** `precedent(phase)` reads this phase's past faults. It hands them to the agent as "WHAT WENT WRONG ON THIS PHASE BEFORE", capped at 600 characters, and keeps them on the building row. The Plan shows them as "failed before — the agent was told".
- **Agents table.** Each agent has its fault records in full (time, mode, phase, request size, error) plus counts per mode. Faults of no one agent are listed separately.
- **Tests:** `test-agent-record` 30/30, including AR-34, a round trip through the real `fault_log`. The inject, phase, prove, escalation, build and work-surface suites also pass.
